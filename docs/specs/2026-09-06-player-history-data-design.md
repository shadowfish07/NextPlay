# NextPlay 游玩档案：第一版数据采集与保留设计

创建日期：2026-09-06；更新日期：2026-09-07。状态：数据优先方向及归档方案已确认；核心代码已实现并进行本地/Android 验证。已复用个人版 OneDrive 的 rclone 授权，真实上传、下载校验与恢复验收通过；生产持续采集尚未启用。

## 1. 目标与完整性的边界

先保存以后无法补回的原始状态和操作事件，再逐步提供前端分析。第一版不得因暂不展示某类数据而省略本文规定的采集链路。

“完整”指已定义的数据源、账号范围和采集频率内，保留收到的完整业务响应及每次观察记录；不承诺获取所有 Steam 内部数据，也不承诺捕获两次轮询之间的全部变化。首次采集是基线，不生成虚构的购买、首次开玩或成就解锁事件。

第一版跟踪主动绑定并开启记录的账号，以及其成功游戏库快照发现的游戏。未绑定账号不采集。Steam 用户 ID 使用字符串，游戏 AppID 使用整数，两者不得混用。软件、未知类型及用户隐藏的游戏照常采集，过滤只影响展示。

## 2. 当前仓库依据

- `lib/data/service/steam_api_service.dart`：客户端直接调用 GetOwnedGames、GetPlayerAchievements；游戏时长当前只映射部分字段，成就当前仅聚合总数及已解锁数。
- `lib/domain/models/game/steam_player_data.dart`：保存当前时长、最后游玩时间和成就计数，无历史快照。
- `lib/domain/models/game/user_game_data.dart`：已有状态、笔记、自定义标签、队列加入时间等当前状态；没有个人评分字段。
- `lib/data/service/game_database_service.dart`：状态更新、批量更新、队列增删、排序和清空都是需要接入事件记录的写入路径。
- `services/igdb`：已有 Bun 服务及 SQLite 资料/评分缓存，可以复用运行环境；个人历史必须使用独立持久存储及账号访问控制，不能继承公共资料接口的访问边界。

## 3. 必须采集的数据清单

下表频率为第一版默认目标，可配置并记录配置版本。任务延迟、限流和无法访问必须显式反映在覆盖率中，不允许宣称采集完成。

| 数据集 | 来源与原始字段 | 频率与覆盖范围 | 可补历史与缺失语义 |
|---|---|---|---|
| 游戏库与时长 | GetOwnedGames；完整响应、game_count、appid、name、playtime_forever、playtime_2weeks、rtime_last_played；实际返回的各平台累计时长、离线时长及其他字段一并保留 | 绑定时立即建立基线；此后每小时完整采集，不设 appids_filter，包含已玩免费游戏 | 不能还原基线之前的每日时长；可选字段不存在不等于零；返回集合不代表购买流水或完整授权清单 |
| 近期游玩补充 | GetRecentlyPlayedGames；完整响应、游戏集合及各项时长 | 每小时，与游戏库分别记录任务结果；不人为截断列表 | 补充近期发现的游戏，不作为拥有证明，不与累计时长或游戏库结果重复相加 |
| 每游戏成就状态 | GetPlayerAchievements；apiname、achieved、unlocktime 及全部返回字段 | 首次发现游戏入队建立基线；近期活跃游戏每 6 小时；所有仍在范围内的游戏每周核对 | 有效解锁时间可以补入历史，但标注回填和观察时间；缺失或零时间戳不猜日期；失败不等于无成就 |
| 每游戏个人统计 | GetUserStatsForGame；stats 中的名称、数值及完整响应；若含成就也保留原始数据 | 与成就任务同批调度，分别记录结果；先验证各游戏接口支持情况 | 游戏自定义计数器未必单调，也未必具有跨游戏统一单位；不把统计重置解释为负活动量；不支持与暂时失败分开 |
| 成就及统计定义 | GetSchemaForGame；成就标识、名称、描述、隐藏标记、图标引用，统计定义及其他返回字段 | 每游戏首次采集；每周刷新；出现未知标识时触发刷新 | 按语言和内容版本保存；总成就数量可能改变，历史完成率必须关联当时定义 |
| NextPlay 操作事件 | 状态变更、笔记修改/清空、标签变更、队列加入/移除/排序/清空，以及批量操作；前后值与作用对象 | 每次成功写入时在同一客户端数据库事务内记录事件及待上传项 | 只能从启用事件记录后完整积累；已有本地状态只导入 baseline，不伪造旧操作；未实现的个人评分不算现有必采字段 |
| 游戏资料版本 | 现有 IGDB、Steam 本地化、VGC 数据源实际取得的完整业务数据；稳定标识、分类及名称、发行信息、评分/分项/状态、来源、语言、上游获取时间 | 跟踪游戏首次建立资料基线；每日检查到期任务，资料最长 7 天核对一次，评分目标每日一次；按来源能力限流、退避；日常请求得到新内容也归档 | 记录观察到的版本，不承诺捕获期间所有改动；缓存命中不是新上游采样；无评分不等于零分；保存媒体引用，不承诺归档图片二进制 |
| 采集与覆盖记录 | 调度时段、账号/游戏/数据源、请求范围、开始/结束时间、HTTP 与业务状态、重试次数、完整性、响应引用、解析和采集配置版本 | 每次任务及每次尝试 | 失败、跳过、部分成功、未支持、未知必须可区分；避免只保留最后成功时间而掩盖缺口 |

“近期活跃”默认指最近 14 天返回近期游玩信息，或在本服务最近 14 天观察到时长增加的游戏。新发现游戏不受活跃筛选限制，必须进入首次基线队列。曾发现但当前不再可见的游戏保留历史，暂停常规个人成就/统计轮询，每周探测恢复情况；它们的覆盖状态标记为当前不可见。多个来源发现同一 AppID 时合并调度，不合并或丢弃来源记录。

接口不支持应有明确证据；模糊错误归类为 unknown，降低频率后重试。每个账号应能查询各数据集的已覆盖、待采集、失败、不可访问和不支持数量。不得用一条“同步成功”掩盖尚未完成的成就或统计基线。

## 4. 公共数据封装与建议存储实体

以下为逻辑实体，物理表结构在实现提案中确定。第一版可以使用独立 SQLite 数据库，不需要引入专用时序数据库。

| 实体 | 必须保存的内容 |
|---|---|
| tracking_accounts | 内部账号 ID、Steam 用户 ID、绑定/停用时间、跟踪配置版本、展示时区历史、凭据引用；不存明文 API Key |
| collection_runs / attempts | 稳定任务 ID、调度槽位、尝试 ID、数据集、目标、状态和错误分类、起止时间、下次重试时间、覆盖与完整性证据 |
| raw_payloads | 去除凭据后的完整业务响应、内容哈希、编码/压缩版本、响应类型及解析版本；账号数据按账号隔离去重 |
| observations | 观察 ID、任务和原始响应引用、observed_at、source_updated_at（若有）、请求参数语义、来源版本、语言、质量标记；相同响应仍保留新观察 |
| library_snapshots / playtime_samples | 完整游戏集合及每游戏实际存在的时长字段；关联 observation，分钟以整数保存，不先四舍五入为小时 |
| achievement_samples / stat_samples | 每账号、AppID、稳定键及原始值、源时间（若有）、定义版本；区分未提供、明确空值、零值和解析失败 |
| metadata_versions | AppID 与来源实体映射、有效观察时间、内容哈希、版本数据；保留评分算法/标签等上游提供的解释信息 |
| user_events / client_outbox | event_id、account_id、app_id 或队列作用域、事件类型、前后值、device_id、设备序号、客户端时间、服务端接收时间、批操作 ID、schema_version |
| derived_views | 当前状态、增量、日报、里程碑等可重建投影及算法版本，不作为唯一历史存储 |

原始业务响应只覆盖表中明确的数据源，不存认证请求、Cookie、Authorization、带 key 的 URL 或异常对象中的请求配置。失败响应先脱敏；非业务 HTML/网关错误只留受限大小的脱敏诊断，不按业务快照长期归档。未知业务字段保留，已知秘密字段必须移除。正文与脱敏规则均需版本化。

## 5. 时间、增量与异常契约

- 所有时间保存为 UTC；原始源时间也保留。按账号 IANA 时区生成日视图，时区设置变更作为配置历史保存。夏令时日不能固定假定为 24 小时。
- 区分 occurred_at（源报告或客户端声明）、observed_at（实际观察）、received_at（服务端接收）与 scheduled_for（计划采样）。不使用计划时间冒充实际时间。
- 时长差表示两次有效观察之间报告的累计变化，不表示精确的会话起止或活跃操作时长。窗口跨日、延迟补报或漏采时，保留未分配增量与质量标记，不擅自平均分配到每天，也不全归入恢复当天。
- 每游戏增量分别计算，再按稳定统计范围汇总。新出现且已有 100 小时的游戏只建立基线，不计作当天新增 100 小时。游戏移出当前库不删除历史、不生成负游玩时长。
- 累计值减少时保留原始样本与 correction 标记，开始新的比较段；不生成负活动量，也不简单截断为零后丢失异常证据。
- 空对象、缺少 games、权限失败或数量突降都不直接生成游戏移除事件。结构、数量及请求范围验证后仍有歧义时记 uncertain；后续独立有效采样确认持续缺席，才生成“观察到不再可见”，不得标注退款或卸载。
- 成就完成率同时保存/关联解锁集合和定义版本。新增成就造成比例下降与用户重置成就是不同事实；两者均不能覆盖旧状态。

## 6. 采集可靠性与客户端事件

服务端任务队列必须持久化；以账号、数据集、目标、调度槽位形成唯一任务键，通过租约防止多个实例重复执行。同一任务的重试记录保留，结果提交保持幂等；运行中任务与进度在重启后可恢复。使用限并发、来源级限流、退避和抖动；限流时保留待处理工作并暴露延迟。

历史槽位未采到就记录缺口。重启后的新请求只产生当前观察，不能填成历史成功。每游戏任务失败不回滚同批其他游戏的已成功数据；同一个完整游戏库快照则必须原子提交。

用户操作需在 App 本地写入事务中同步写入事件/outbox，上传成功后标记确认；重试使用相同 event_id。离线期间事件持续累积，重新联网后补传。客户端时钟不可信，保留设备序号和服务端接收顺序，不声称多设备事件具有精确全局发生顺序。并发修改保存所有事件及冲突信息，当前状态投影采用版本检查，禁止无提示覆盖。

迁移旧本地数据时，一次性导入当前状态和完整队列顺序并标为 baseline。状态来源要区分用户操作、导入和自动规则，避免上游同步制造虚假用户行为。绑定切换时 outbox 必须维持原账号归属，不能上传到后来登录的账号。

服务端自动采样和客户端事件记录是第一版数据完整性的两个交付项；只上线服务端轮询不能宣称个人档案数据已全。

## 7. 保留、访问和恢复

- 原始业务响应、观察记录、结构化历史及个人操作事件默认长期保留，不设置自动过期。通过压缩和内容去重节省空间，但不能丢失未变化时的观察证据。
- 长期保留任务摘要、失败分类和缺口；临时诊断日志默认 30 天。派生聚合和当前状态可删除重建，原始历史不能按缓存清理。
- 每日产生可验证的一致性备份，建议保留 30 个每日版本和 12 个月度版本，并复制到独立故障域。数据库启用 WAL 时不得直接只复制主数据库文件；使用一致性备份机制。
- 上线前演练从备份恢复到空环境，核对记录数量、哈希、外键关联以及派生数据重建。每日备份意味着灾难情况下仍可能损失最近 24 小时数据；应在运维状态中明确，不宣称零丢失。
- API 读取、导出、事件写入和原始响应访问必须验证账号归属。不能仅凭任意 Steam ID 获取个人档案；也不能把用户 API Key 自动从客户端上传到服务器。
- 自动采集使用服务端独立配置的可用凭据与明确的账号绑定；具体凭据是否能访问目标账号须验证，绑定本身不能绕过 Steam 可见性限制。
- 停用跟踪停止后续采集，历史保留；删除档案是单独操作，删除账号关联数据及未上传事件，并记录防止备份恢复后重新出现数据的删除标记。备份中的残留按保留周期淘汰，恢复时先应用删除标记再开放访问。
- 生产数据库、原始响应、备份、截图与日志全部是仓库外或 ignored 数据，不提交 Git。提供版本化导出（数据、事件、观察、定义和来源索引），支持以后迁移。

### 7.1 容量预算

以 1 个账号、500 款游戏、10 款近期活跃游戏及第 3 节频率估算，不保存图片或视频二进制。以下是容量规划区间，不是实测值或上限；不含首次全量基线、备份副本、WAL、临时打包和恢复空间。

| 数据 | 每日新增估算 | 每年新增估算 |
|---|---:|---:|
| 未压缩原始业务响应 | 10–100 MB | 4–37 GB |
| 去重、压缩后的原始归档 | 2–20 MB | 0.7–7.3 GB |
| 本地结构化历史及索引 | 0.5–5 MB | 0.2–1.8 GB |

三行不是直接相加的独立长期副本：未压缩响应处理后转入压缩存储。以每游戏响应平均 300 字节作示例，游戏库单项为 500 × 300 × 24 ≈ 3.6 MB/天；成就、stats、资料及评分正文大小决定额外开销。多个账号的私人数据随账号数增长，公共资料可共享版本。

首次上线连续统计至少 7 天的各数据集响应字节数、去重率、压缩率、数据库实际大小和待归档量，分别报告基线成本及日常增长，再更新预算。不能把估算当作磁盘容量保证。

### 7.2 本地查询与云端归档

- 本地 SQLite 保存结构化历史、当前状态、事件、观察和归档索引；原始响应正文采用独立压缩文件存储，数据库中的 raw_payloads 保存哈希、位置和存储状态。迁走正文不删除逻辑记录或观察引用。
- 同样的结构化状态可以使用状态版本加观察引用，保留每次成功观察而不重复复制整组字段。常规时长与成就查询不依赖 OneDrive 在线。
- 原始数据每天封存为不可变归档包，使用版本化清单和压缩格式（第一版建议 JSONL + gzip），文件名包含日期和唯一包 ID；超过实现设定的包大小后分包，避免大量单响应小文件。
- 每个包保存完整业务对象、记录标识、来源及观察关联；manifest 保存格式版本、对象哈希、记录数、包大小及包 SHA-256。去重对象与所有引用的位置必须可解析，恢复不能只依赖尚存的本地索引。
- OneDrive 长期保存归档包及可恢复的数据库备份。本地原始数据默认保留最近 7 天；按上述预算约为 14–140 MB，另加未完成归档、数据库、日志、备份和临时空间。长期保留的含义是本地或已验证云端至少有可访问的内容，不要求两边永久持有全部正文。
- 活跃 SQLite 放在普通本地目录，使用一致性备份机制导出后上传。归档通过 Microsoft Graph 直接上传，不依赖桌面同步目录释放空间；OneDrive 按需文件只是人工查看归档的可选方式。
- 首次接入需要用户完成 Microsoft 账号授权，配置专用归档目录并验证容量及上传/下载能力。凭据只在安全的本机配置或凭据存储中保存，不进入原始数据包、日志或 Git。

### 7.3 上传、校验和清理契约

归档状态按 building → sealed → uploading → verified → local_evicted 持久化。失败记录错误及重试信息，不能越过 verified 直接清理本地内容。

1. 在临时文件中完成包及 manifest，校验完整性后原子封存；上传期间不再修改正文。
2. 使用唯一包名上传；大包使用可续传会话，重复执行不能覆盖其他归档。网络超时后先核对远端状态，不假定提交失败或成功。
3. 确认远端提交完成，下载完整包进行流式 SHA-256 校验，并核对 manifest。只有校验一致才标记 verified；不能把 ETag 当作 SHA-256。
4. 在本地事务中记录远端 drive/item 标识、包哈希、对象位置和校验时间。manifest 必须也已上传并验证；校验、提交索引和清理之间任一阶段崩溃，重启都必须幂等恢复。
5. 仅清理已 verified 且超过 7 天保留期的本地原始正文。记录本地已释放状态，保留全部引用；删除前重新检查无未归档依赖。
6. 历史重解析按索引下载对应包并再次校验，使用有容量限制的临时缓存。远端不可访问或校验失败时明确报错，不生成空结果。

备份与归档共同组成恢复集：数据库备份引用的对象要么存在于已验证归档中，要么包含在该备份配套的原始数据包内。只有依赖对象和 manifest 都已验证，才宣布恢复集可用。定期从云端恢复到空目录并重建索引，不能只验证本地残留文件。原始归档独立于 30 日/12 月的数据库备份轮换，不随备份过期删除。

### 7.4 空间不足、删除与验收

- 归档失败、账号授权过期或云端配额不足时保留本地待上传数据并报告；监控本地剩余空间、未归档字节数、最老待归档时间和最近成功校验时间。
- 设置可配置磁盘低水位，预留数据库写入及任务收尾空间；接近阈值时暂停新增外部采集并记录缺口，禁止删除未归档的唯一副本。客户端未获服务端持久化确认的事件继续留在 outbox。
- 原始包已迁走后，云端是这些内容的长期保存位置，不能将其当作可随意删除的缓存。常规查询数据库备份不能替代原始包；单个 OneDrive 也不等于有第二份独立原始档案副本。
- 个人原始归档按账号分包，避免多个账号混装。删除档案时同时清理远端账号包和缓存；公共资料包独立保存。备份中的历史个人数据按既定轮换及删除标记处理。
- 实现必须验证：正常归档与本地释放、断网续传、重复上传、内容损坏、manifest 缺失、上传后崩溃、授权过期、云端满额、本地低水位、仅从云端恢复及历史重解析。展示磁盘数据时区分数据库实际占用、缓存、待上传与云端归档量。

## 8. 明确不在第一版采集范围内

以下范围是显式排除，不能在产品中承诺以后可以完整补回：

- 高频在线状态、正在玩的游戏和精确会话：小时轮询不能完整捕获，若需要需单独确定采样成本及准确度。
- 购买价格、订单、退款原因、真实购买时间：现有游戏库接口不提供这些事实，需要其他数据源或用户录入。
- 好友关系、聊天、交易库存、徽章/等级、整个 Steam 市场的价格或在线人数历史：与个人游玩档案第一版无直接依赖，暂不新建采集源。
- 任意游戏的全部内部进度：仅保留 Web API 实际公开的个人 stats，不能访问未公开存档或内部指标。
- 尚未实现的个人评分功能：未来实现时必须从第一天记录修改事件。

## 9. 第一版验收标准

1. 对表中每个数据集有源适配器、持久存储、独立覆盖状态和调度/事件入口；不允许因无前端而省略成就、stats 或客户端事件。明确不支持的游戏可记为 unsupported，无法判断的错误不能算支持性验证通过。
2. 使用脱敏固定样本验证：未知字段保留、字段缺失与零值区分、完整集合、平台时长、定义变更、成就解锁/重置、stats 非单调变化均可回放。
3. 两次相同响应只存一份业务内容，仍可查到两个观察；同一任务重试和重复事件上传不产生重复逻辑记录。
4. 模拟权限变化、空响应、部分失败、429、超时、崩溃和恢复，证明无虚假零值、无虚构历史补采、无已成功数据丢失。
5. 用跨午夜、漏采、离线补报、累计回退、新游戏已有时长、游戏缺席和时区变更样本，验证增量和不确定标记。汇总不重复计算多来源或平台字段。
6. 在 Android 实际验证离线状态/笔记/标签/队列事件持久化、进程重启、恢复上传、批量操作及账号切换；尚未提供写入入口的字段通过真实仓库写入路径验证并披露范围。
7. 实际目标服务验证重启续跑、租约和每类数据的存储链路；Steam 外部接口按显式 live smoke 流程验证可用账号与游戏，未覆盖游戏明确标注，不能用 fake 冒充真实覆盖。
8. 验证账号隔离、凭据脱敏、数据导出、停用/删除以及完整备份恢复。删除所有派生表后可以重建一致结果。
9. 代码阶段完成 `tool/verify_fast.sh`、真实构建及受影响运行时验收。前端最初可只展示时长趋势，但采集覆盖和失败状态必须可检查。
10. 按第 7 节验证 OneDrive 归档、云端恢复及磁盘保护；在授权的目标 OneDrive 目录完成真实上传、下载校验和恢复，模拟测试不能替代实际接入验证。

## 10. 实施顺序与来源

实现按共同封装/账号边界与历史库 → Steam 库/时长 → 成就/统计/定义 → 资料归档 → App 事件/outbox → 恢复/导出与验收推进。尽早启动库/时长采样可以提前积累数据，但在其余必采链路完成前只能称为部分上线。

实现提案、需求场景、任务清单及验收边界见 `services/igdb/openspec/changes/add-player-history/`。已进行隔离的真实 Steam 采集验收；不表示生产已部署或正在持续采集。

## 2026-09-07 交互修正

App 历史功能复用现有后端与已保存的 Steam 凭据，自动完成账号认证和上传。设置页只提供状态与立即同步，不要求填写服务地址或历史令牌。服务端将 Steam ID 与显式配置的凭据一并校验，不能仅凭公开账号 ID 读取历史。旧手动连接配置在启动时清理。
